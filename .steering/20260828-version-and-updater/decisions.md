# decisions — 版表示とアプリ内アップデート

## 2026-08-28: インストール元で更新の振る舞いを分ける

Homebrew cask が主配布経路である一方、Releases から直接入れたユーザーもいる。
アプリが経路に関わらず自己置換すると brew 側の版情報が必ずずれ、次の
`brew upgrade` で状態が食い違う。逆に導線提示だけに留めると、直接経路の
ユーザーには更新手段が無い。

`<brew prefix>/Caskroom/awayview` の存在で経路を判定し、`homebrew` では
コマンド提示のみ、`direct` では自己置換まで行う。

## 2026-08-28: 適用はユーザー操作のときだけ

チェックは無人で回すが、適用は必ずメニュークリックを起点にする。
更新は自プロセスの再起動を伴い、再起動の瞬間の表示状態がホーム学習に影響する。
ユーザーが押す瞬間は画面を見ている瞬間なので、事故の窓が構造的に狭い。

加えて `WatchState` が LOW 系のときは適用自体を拒否する。操作起点だけでは
リモート接続中に押される可能性が残るため、状態でも塞ぐ。

## 2026-08-28: Sparkle を入れない

自動更新の定番だが、EdDSA 鍵と appcast のホスティングが増え、依存ゼロだった
構成に大きな外部依存が入る。しかも brew との二重管理は Sparkle でも解けない。
必要なのは「GitHub Releases を見て、署名を検証して、置き換える」だけで、
Security.framework と URLSession で足りる。

## 2026-08-28: `UpdateInstaller` に自動テストを書かない

自分自身のバンドルを消して置き換える操作は、意味のあるテストにするなら本物の
バンドルと署名済み zip が要る。CShim の ENOMEM リトライで同じ判断をしたのと
同様に、割に合わないと判断した。CLI フラグ経由の実機確認で代替し、穴は
tasklist に明記する。
